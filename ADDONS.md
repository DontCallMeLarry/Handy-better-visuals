# Addons (fork-local features)

This fork tracks upstream [cjpais/Handy](https://github.com/cjpais/Handy) and adds features
that upstream does not carry. The goal is that `git pull upstream main` stays boring.

Handy is a compiled Tauri binary — there is no plugin runtime and no npm package to update,
so a genuinely out-of-tree plugin is not possible. What is possible, and what this layout
does, is keep essentially all addon code in **new files that can never conflict**, and reduce
the edits to upstream files to a handful of single lines.

## The upstream diff, in full

Every edit to an upstream file is tagged `handy-addon`. That is the complete list — grep for
it to re-apply after a conflicted merge:

```
git diff upstream/main --stat -- src-tauri/src/lib.rs src-tauri/src/tray.rs \
  src-tauri/src/shortcut/handler.rs src-tauri/src/actions.rs \
  src/components/settings/advanced/AdvancedSettings.tsx
grep -rn "handy-addon" src-tauri/src src --include='*.rs' --include='*.tsx'
```

| ------------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------ |
| `src-tauri/src/lib.rs`                                  | 1                                  | `mod addons;`                                                |
| `src-tauri/src/lib.rs`                                  | 1                                  | `addons::init(app_handle);` in `initialize_core_logic`       |
| `src-tauri/src/lib.rs`                                  | 1                                  | First `on_window_event` match arm, skipping addon windows    |
| `src-tauri/src/tray.rs`                                 | 1                                  | `addons::on_tray_state(app, state);` in `set_tray_state`     |

| `src/components/settings/advanced/AdvancedSettings.tsx` | 6                                  | Three imports + three JSX rows                               |

With the explanatory comments, the whole upstream diff fits on one screen. `git diff upstream/main --stat`
on the files above shows it. Nothing else upstream is touched.

These in particular are deliberately **not** modified, because they are the repo's worst
merge-conflict surfaces:

- `src/bindings.ts` — generated by tauri-specta, rewritten on every debug build, and edited
  upstream constantly. Addons therefore add **no Tauri commands**; the frontend talks to Rust
  over the event bus instead (a frontend `emit` reaches Rust `app.listen`).
- `src-tauri/src/settings.rs` / `src/stores/settingsStore.ts` — addon config lives in its own
  store file (`addons_store.json`), not in `AppSettings`.
- `src/i18n/locales/*/translation.json` — addons register their own i18next namespace at
  runtime. This also dodges CI's `check:translations`, which fails when a key exists in `en`
  but not in the other 23 locales.
- `vite.config.ts` — addon HTML lives in `public/`, which Vite copies to the dist root
  verbatim, so no new Rollup entry is needed.
- `src-tauri/capabilities/*.json` — addon windows use no Tauri JS API, so they need no ACL
  entry. Rust drives them with `eval`, which is not ACL-gated.

## Layout

```
src-tauri/src/addons/
  mod.rs                       registry: init(), on_tray_state(), owns_window()
  prominent_glow/
    mod.rs                     config, persistence, frontend event bridge
    surface.rs                 the window pool (all platforms)
    macos.rs                   NSPanel specifics (tauri_panel! needs its own module)
  repaste_chord.rs             twin-modifier detection, re-paste, config
src/addons/prominent-glow/
  ProminentGlow.tsx            settings rows
  useProminentGlow.ts          event-bus hook (no Tauri commands)
  i18n.ts                      runtime i18next namespace
  index.ts
public/prominent-glow.html     the glow itself: standalone HTML+CSS, no bundler
src/addons/repaste-chord/
  RepasteChord.tsx             settings row (toggle)
  useRepasteChord.ts           event-bus hook (no Tauri commands)
  i18n.ts                      runtime i18next namespace
  index.ts
```

## Keeping up with upstream

```bash
git fetch upstream
git merge upstream/main          # or: git rebase upstream/main
```

If a hook line conflicts, re-apply it from the table above. Addon windows are all labelled
`handy_addon_*`, so nothing upstream adds can collide with them.

## Addon: Prominent recording glow

**Setting:** Advanced → App → _Prominent_ (plus a _Glow intensity_ slider once enabled).

While recording, every attached display is covered by a full-screen, click-through,
always-on-top window painting a soft orange vignette inward from all four edges. The centre
60% × 60% of each screen is left completely untinted at any intensity. It turns off the moment
recording stops (including on cancel and on error) and fades rather than snapping.
Two fully clear windows, opposite each other, revolve clockwise around the screen once
every ~10 s so the glow reads as live rather than as a stuck tint.

It is independent of `overlay_style` — you can run it with the pill overlay off, which is the
Linux default and the likely setup for anyone who wants this.

### How it works

- **Trigger.** Hooked into `tray::set_tray_state`, the single function every recording
  start / stop / cancel / error path calls, on every platform, regardless of overlay and tray
  settings. `TrayIconState::Recording` turns the glow on; anything else turns it off.
- **Windows are pooled and never destroyed.** Upstream's app-wide `CloseRequested` handler
  calls `prevent_close()`, hides the window, and on macOS flips the app to
  `ActivationPolicy::Accessory` — so closing a glow window would fail to destroy it _and_ make
  the Dock icon disappear. The pool only grows; surplus surfaces are hidden.
- **Hot-plug** is handled by re-enumerating displays and re-placing on every show, rather than
  by subscribing to a platform display-change notification. Surfaces beyond the current
  display count are explicitly hidden, so unplugging a monitor cannot stack two glows onto one
  screen.
- **Click-through** is per-platform, and deliberately not uniform:
  - macOS: `ignoresMouseEvents` via the panel builder (applied synchronously during build;
    Tauri's `set_ignore_cursor_events` is dispatched async and would leave the first frame
    swallowing clicks across the whole screen).
  - Windows: `set_ignore_cursor_events(true)`, which tao stores as a window flag and
    re-derives `WS_EX_TRANSPARENT | WS_EX_LAYERED` from on every style change — hand-setting
    the bit would be wiped by the first `show()`.
  - Linux: an empty GTK input shape. Tao's `set_ignore_cursor_events` installs a 1×1 region
    at (0,0) rather than an empty one, which would leave a live input pixel sitting exactly on
    the GNOME/KDE top-left hot corner.
- **Rendering.** The vignette is a WebGL fragment shader over one full-screen triangle
  per display, which is what makes the two revolving clear windows (180° apart, one
  revolution per `--glow-spin-period`, default 10 s) affordable: GPU fill only, no
  per-frame CSS repaint. A CSS-only rotation was rejected twice — an animated
  `conic-gradient` mask re-rasterises a full-screen mask on the CPU every frame, and a
  `transform: rotate` on a masked element needs a diagonal-sized (`142vmax`) backing
  store, ~300 MB per 5K display. Enter/leave fade and the breathing pulse stay CSS
  opacity animations on the compositor. The original CSS gradient layers remain in the
  page as the fallback: no WebGL, a lost context, or `prefers-reduced-motion` leaves the
  glow on screen, static.

### Known limitations

- The glow **is captured** in screenshots, screen recordings and screen shares (this matches
  the existing pill overlay). macOS could opt out with `NSWindowSharingType.none` and Windows
  with `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`; neither is wired up.
- Windows: excluded from the taskbar, but not from Alt-Tab. The reliable exclusion is
  `WS_EX_TOOLWINDOW`, which tao would overwrite on the next style diff.
- Linux: on a compositor without `zwlr_layer_shell_v1` (notably GNOME) and on X11, the
  fallback path relies on the `Notification` window type hint for stacking, which some window
  managers honour better than others.
- UI strings are English only; other languages fall back to English via `fallbackLng`.

## Addon: Extra recording buffer, surfaced

**Setting:** Advanced → Transcription → _Extra Recording Buffer_ (0–1500 ms).

Not new behaviour: upstream's `extra_recording_buffer_ms` keeps the mic open for that
long after the stop press so the last word is not clipped, but only exposes it in the
Cmd+Shift+D debug tab. This addon renders the same `RecordingBuffer` component in the
Advanced tab — same setting key, same Rust path, nothing duplicated. The default stays
`0` (an upstream test asserts it); set it once and it persists.

The Prominent glow deliberately still fades on the stop press, not at the end of the
buffer: the pill overlay and tray switch to "transcribing" at the press, and the glow
following them is the user's acknowledgement that the press registered.

## Addon: Re-paste chord

**Setting:** Advanced → Output → _Paste again shortcut_ (on by default).

Hold Left Command, then press Right Command, and Handy pastes the last pasted text again.
Nothing records, and the press never reaches the coordinator. The general rule is the transcribe key pressed while its other-side twin is held. It needs a one-side modifier shortcut such as `command_right`. It is macOS only. The paste goes through the normal
`utils::paste` path, so paste method, clipboard handling and auto-submit all apply. Config
lives in `addons_store.json` under `repaste_chord`.

### How it works

- **Hook.** `intercept_shortcut` is an early return at the top of `handle_shortcut_event`. It
  sees every `transcribe` event before upstream does.
- **Detection.** handy-keys fires the Right Command hotkey even with Left Command down. At
  that press the addon reads the physical modifiers with `CGEventSourceFlagsState`. If the
  twin is down and the tray is idle, it swallows the press and its release.
- **Paste under the held key.** If Left Command is still down when Right Command comes up, the
  addon pastes at once, on every tap. It swaps the clipboard like `utils::paste`, then taps
  only V with the held modifier flags. It never sends a synthetic Command-up. That event would
  clear the held key at the HID level, and the next tap would start a recording.
- **Paste after keys up.** Otherwise a thread waits up to 2 s for both keys to come up. Then it
  pastes through the normal paste path. The addon also takes this path when the paste method
  is not Cmd+V, or when auto-submit or reliable paste is on.
- **Which text.** The newest text the pipeline pasted before the press. A one-line hook,
  `addons::on_paste(&final_text)` in `actions.rs`, fills an in-memory ring of two just before
  each paste. On a fresh launch the ring is empty. It then falls back to the newest non-empty
  history entry, post-processed text first.
- **No nested locks.** The hook runs on the handy-keys thread. A lock held across a call that
  locks again freezes every shortcut, so each guard drops before the next call.
- **Events.** The frontend talks to Rust over `handy-addon:repaste-chord:{get,set,state}`.
  No Tauri commands, so `bindings.ts` stays untouched.

### Known limitations

- Right Command first, then Left Command, records as usual.
- A transcribe shortcut with a key, such as `option+space`, gets no chord.
- The chord does nothing while recording or transcribing. That press goes to the coordinator.
- With nothing ever pasted and an empty history, the chord only logs.
